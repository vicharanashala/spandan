# Spandan Response Service — Context File

## Project Identity
- **System:** Spandan — a classroom engagement analytics platform
- **Service:** Response Service (bounded context: Immutable Interaction History)
- **Architecture:** Clean Architecture layered inside a Spring Boot microservice
- **DB-per-service:** yes — owns `response_db` exclusively

## Core Responsibility
**Single source of truth for all raw student interactions.** Owns the permanent, immutable history of everything that happened during a session: which question was displayed to which student, when, what they answered (if anything), whether it timed out, and whether the answer was correct. Never modifies or deletes stored interactions — only appends. Answers: **"What happened, to whom, when, in what order, and was it correct?"**

Response Service persists facts. It does NOT compute analytics, engagement, mastery, trends, or reports.

## Interaction Framework Role

Response Service is the **immutable interaction store** sitting between RTC and Analytics:

```
Question Generation Service  ←── produces educational metadata + correct answers
        ↓
  Polling Service  ←── opens/closes polls
        ↓
  RTC / Gateway Service  ←── manages display timing, detects answer/timeout, publishes interaction events
        ↓
  Response Service  ←── YOU ARE HERE
  ┌─ Consumes QuestionDisplayedEvent, QuestionAnsweredEvent, QuestionTimedOutEvent
  ├─ Persists unified interaction records (immutable, append-only)
  ├─ Calculates correctness (selectedAnswer vs correctAnswer from QGS)
  ├─ Produces InteractionPersistedEvent and SessionInteractionCompletedEvent
  └─ Exposes raw interaction history via read-only REST APIs
        ↓
  Analytics Service  ←── consumes raw interactions, derives engagement/mastery
        ↓
  Reporting Service  ←── generates dashboards, exports
```

Response Service never communicates directly with RTC, Polling Service, QGS, Analytics, or Reporting — all communication is event-driven via Kafka.

## Key Architecture Decisions

### CP + Strong Consistency (MANDATORY)
Exactly one interaction record per student per question per display. No duplicates, no gaps, no overwrites.

| Decision | Implementation |
|---|---|
| Immutable append-only write model | INSERT only — no UPDATE, no DELETE on interaction records |
| Unique constraint on eventId | `UNIQUE(event_id)` prevents duplicate event processing |
| Business unique constraint | `UNIQUE(student_id, question_id)` — one interaction per student-question pair |
| Kafka consumer `idempotence=true` | Producer-level dedup on `interaction-events` topic |
| DB upsert with unique constraints | `ON CONFLICT (event_id) DO NOTHING` — second write of same event is silently ignored |
| Server-assigned event-id | All events carry `eventId` (UUID) generated by RTC — RS deduplicates on this |
| Interaction order preserved by `eventTimestamp` | No reordering, no gap-filling — raw chronological order |
| Projection tables derived from interactions | Question tallies are computed at query time, not stored separately |
| No external REST endpoints for write | All interaction data arrives via Kafka — no POST/PUT/DELETE for interaction submission |

### Why CP over AP
- A student's complete interaction history is the permanent source of truth — duplicates or gaps corrupt analytics permanently
- Educational audit trails require deterministic, immutable records
- The cost of rejecting a duplicate during a partition (retry later) is acceptable compared to the cost of an undetectable duplicate

### Immutable History Model
- `QuestionDisplayedEvent` → interaction record created (questionDisplayedAt set, answered=false, timeout=false)
- `QuestionAnsweredEvent` → interaction record updated with answer fields + correctness (answered=true, timeout=false)
- `QuestionTimedOutEvent` → interaction record updated with timeout fields (answered=false, timeout=true)
- Once any field is set, it is never overwritten with a different value
- Raw events are stored in a separate `raw_events` table for audit/replay

### Correctness Determination
Response Service is the **single owner of correctness calculation**:
- QGS publishes `QuestionGeneratedEvent` containing `correctAnswer` for each question
- RS stores `correctAnswer` per question in a `question_metadata` table
- When `QuestionAnsweredEvent` arrives, RS compares `selectedAnswer` vs `correctAnswer`
- Result (`isCorrect`, `correctAnswer`) is persisted in the interaction record
- No downstream service recalculates correctness

### CAP Theorem Analysis
| Aspect | Choice | Rationale |
|---|---|---|
| Consistency | **CP** — strong consistency on interaction writes | Duplicate/corrupt interaction history corrupts all downstream analytics |
| Availability | Degraded during partition (writes rejected) | Transient errors are retryable; no data loss |
| Partition Tolerance | Required by distributed nature | Kafka topic, DB cluster |

### Consistency Model
- **Strong consistency** for interaction writes: `SERIALIZABLE` isolation for the upsert pattern ensures exactly one record per student+question
- **Eventual consistency** for read replicas: GET APIs can read from replicas accepting slight staleness
- **Read-your-writes**: Teacher querying immediately after answer period sees the committed interaction

### Event Ordering Guarantees
- **Per-question ordering**: Kafka partition keyed by `questionId` ensures `QuestionDisplayedEvent` arrives before `QuestionAnsweredEvent`/`QuestionTimedOutEvent` for the same question
- **At-least-once delivery**: Kafka consumers are idempotent; duplicate events silently ignored via `eventId` uniqueness
- **No ordering across different questions**: Independent — interactions for question A are processed independently from question B

### Failure & Retry Strategy
| Failure | Mechanism | Recovery |
|---|---|---|
| DB write failure | `@Transactional` rolls back | Kafka consumer retries (up to 3 attempts) |
| Kafka consumer failure | `DefaultErrorHandler` with retry + DLQ | Poison messages routed to DLQ for manual inspection |
| Duplicate event | `ON CONFLICT (event_id) DO NOTHING` | Silently ignored |
| Late-arriving event (answer before display) | Grace period in service — stores answer even without display record | Display record may arrive later (rare, but handled) |
| Question metadata missing for correctness | Correctness deferred until QuestionGeneratedEvent consumed | Interaction stored without isCorrect; backfilled when metadata arrives |
| Network partition | Kafka consumer pauses until reconnected | At-least-once delivery resumes; no data loss |

### Idempotency Strategy
- **Event consumption**: `eventId` (UUID) is unique in the DB — duplicate events result in `ON CONFLICT DO NOTHING`
- **Kafka producer**: `enable.idempotence: true` prevents duplicate broker writes
- **Interaction record**: `UNIQUE(student_id, question_id)` prevents duplicate interaction creation

## Bounded Context: Immutable Interaction History
**Inside:** Raw interaction records, correctness calculation, question metadata storage, history query API
**Outside:** Question content (QGS — not stored), educational hierarchy (QGS — referenced by ID), poll timing (Polling Service — not stored), analytics computation (Analytics Service — reads via REST), display/answer/timeout production (RTC — feeds interaction-events)

### Anti-Corruption Boundary
- Never stores question text or options — only question IDs
- No other service writes to `response_db`
- Other services read via REST GET endpoints — never query response DB directly
- No POST/PUT/DELETE endpoint for interaction data — all writes arrive via Kafka

## Database Schema

### `interactions` table (unified interaction record)
```sql
CREATE TABLE interactions (
    id UUID PRIMARY KEY,
    event_id UUID NOT NULL UNIQUE,
    event_type VARCHAR(20) NOT NULL,  -- DISPLAYED, ANSWERED, TIMED_OUT
    event_timestamp TIMESTAMPTZ NOT NULL,
    session_id UUID NOT NULL,
    lecture_id UUID,
    student_id UUID NOT NULL,
    question_id UUID NOT NULL,
    section_id UUID,
    subsection_id UUID,
    topic_id UUID,
    concept_id UUID,
    learning_objective VARCHAR(500),
    question_type VARCHAR(20),
    difficulty VARCHAR(10),
    question_sequence INT,
    question_displayed_at TIMESTAMPTZ,
    question_answered_at TIMESTAMPTZ,
    response_time_ms BIGINT,
    selected_answer VARCHAR(500),
    correct_answer VARCHAR(500),
    is_correct BOOLEAN,
    answered BOOLEAN NOT NULL DEFAULT FALSE,
    timeout BOOLEAN NOT NULL DEFAULT FALSE,
    event_version VARCHAR(10) DEFAULT '1.0',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(student_id, question_id)
);

CREATE INDEX idx_interactions_session ON interactions(session_id);
CREATE INDEX idx_interactions_student ON interactions(student_id);
CREATE INDEX idx_interactions_question ON interactions(question_id);
CREATE INDEX idx_interactions_lecture ON interactions(lecture_id);
CREATE INDEX idx_interactions_event_id ON interactions(event_id);
```

### `question_metadata` table (from QGS)
```sql
CREATE TABLE question_metadata (
    id UUID PRIMARY KEY,
    question_id UUID NOT NULL UNIQUE,
    correct_answer VARCHAR(500),
    question_type VARCHAR(20),
    difficulty VARCHAR(10),
    lecture_id UUID,
    section_id UUID,
    subsection_id UUID,
    topic_id UUID,
    concept_id UUID,
    learning_objective VARCHAR(500),
    question_sequence INT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### `raw_events` table (append-only audit log)
```sql
CREATE TABLE raw_events (
    id UUID PRIMARY KEY,
    event_id UUID NOT NULL UNIQUE,
    event_type VARCHAR(20) NOT NULL,
    event_payload JSONB NOT NULL,
    consumed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Processing Flow

### Display Event
1. RTC → `QuestionDisplayedEvent` → Kafka `interaction-events`
2. RS consumer deserializes event
3. Stores raw event in `raw_events` table
4. INSERT into `interactions` with `eventId`, `sessionId`, `lectureId`, `studentId`, `questionId`, `questionDisplayedAt`, educational metadata — `ON CONFLICT (eventId) DO NOTHING`
5. Publish `InteractionPersistedEvent`

### Answer Event
1. RTC → `QuestionAnsweredEvent` → Kafka `interaction-events`
2. RS consumer deserializes event
3. Stores raw event in `raw_events` table
4. Looks up `correctAnswer` from `question_metadata` table (by questionId)
5. Calculates `isCorrect = selectedAnswer.equals(correctAnswer)`
6. UPSERT into `interactions`: set `selectedAnswer`, `correctAnswer`, `isCorrect`, `questionAnsweredAt`, `responseTimeMs`, `answered=true` — `ON CONFLICT (eventId) DO NOTHING`
7. Publish `InteractionPersistedEvent`

### Timeout Event
1. RTC → `QuestionTimedOutEvent` → Kafka `interaction-events`
2. RS consumer deserializes event
3. Stores raw event in `raw_events` table
4. UPSERT into `interactions`: set `timeout=true` — `ON CONFLICT (eventId) DO NOTHING`
5. Publish `InteractionPersistedEvent`

### Question Metadata Event
1. QGS → `QuestionGeneratedEvent` → Kafka `question-generation-events`
2. RS consumer extracts `questionId`, `correctAnswer`, `questionType`, `difficulty`, educational hierarchy
3. INSERT/UPDATE into `question_metadata` — `ON CONFLICT (questionId) DO UPDATE`

## Scalability
- **Read replicas**: GET endpoints can scale horizontally using PostgreSQL read replicas
- **Write master**: All Kafka consumers write to a single primary — scale vertically if write volume grows
- **Database indexing**: Indexes on `sessionId`, `studentId`, `questionId`, `lectureId` for query performance
- **Connection pooling**: HikariCP tuned to 10 connections minimum, 20 maximum
- **Kafka consumer concurrency**: Configurable (default 3) — partition by `questionId`

## Security
- **JWT authentication**: Validated synchronously with Auth Service for all user-facing endpoints
- **Role-based access**: TEACHER and ADMIN see all interactions for their sessions; STUDENT sees only their own
- **Internal endpoints**: Analytics support endpoints require `X-Internal-Call: true` header + service token
- **Input validation**: All request parameters validated (UUID format, pagination bounds)
- **SQL injection**: Prevented by JPA parameterized queries
